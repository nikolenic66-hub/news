## 1. Цель продукта

Превратить Васька из чат-собеседника с периодическим мониторингом новостей в надёжного игрового компаньона для групп FC Mobile.

Васёк должен:
- естественно общаться в группе и понимать контекст;
- находить актуальные сведения об игре;
- искать карточки игроков и читать их реальные характеристики;
- сравнивать игроков и объяснять выбор под конкретный режим;
- разбирать скриншоты и составы;
- объяснять события, задания, награды и обновления;
- давать ссылки и показывать, откуда взята информация;
- честно сообщать, когда данных нет или источник не подтверждает ответ.

В обычном чате отвечает коротко. Подробный анализ выдаёт по запросу.

## 2. Текущее состояние

На момент создания документа в репозитории уже есть (перед следующими изменениями состояние следует проверять по коду):
- Telegram-бот на Python с long polling;
- общение через Groq Chat Completions;
- отдельная модель Groq Vision для изображений;
- системный промпт с характером Васька, правилами кратких ответов и маркером [SKIP];
- краткая история группового чата и ограниченная игровая память;
- SQLite-хранилище и накопительные счётчики активности;
- базовые административные команды и команды статистики;
- мониторинг публикаций FC Mobile через Google News RSS;
- отдельный RSS-поиск по формулировке игрового вопроса с ограничением частоты;
- осторожная проверка промокодов по датированным публикациям;
- контекст свежих публикаций передаётся модели при релевантных вопросах.

### Ограничения текущей реализации

- RSS — это новости и выдержки, а не структурированная база карточек.
- Наличие мониторинга не означает, что бот уже умеет достоверно назвать OVR любой карты или её цену.
- Не утверждать, что подключён официальный API RenderZ или EA: в проекте это не подтверждено.
- Google News может индексировать материалы с задержкой и пропускать публикации.
- Модель зрения может ошибаться на мелком/нечётком скриншоте. Запрет угадывать не заменяет проверку на реальных изображениях.
- Цена рынка быстро устаревает и должна сопровождаться временем получения.
- Нельзя заявлять о функции, которая только описана в этом плане.

## 4. Единая модель доверия и свежести

Каждая запись об игровом факте должна по возможности содержать:
- тип: official_news, event, player_card, player_stats, market_price, promo_code, gameplay_rule или community_opinion;
- название и нормализованный идентификатор;
- URL первоисточника;
- источник;
- дату публикации;
- время получения ботом в UTC;
- дату последней проверки;
- статус: official, community, unverified или stale;
- короткий текст или структурированные поля;
- версию игры/сезон, если известны.

### Правила актуальности

1. Не путать дату публикации и дату получения.
2. Не считать старую карточку актуальной только потому, что её страница доступна.
3. Не считать дату в URL доказательством даты события.
4. Для событий хранить начало и окончание с часовым поясом, если они явно известны.
5. Для цен хранить время снимка; не говорить «сейчас стоит», если цена давно не обновлялась.
6. После крупного патча перепроверять сведения о механиках.
7. При противоречии источников показывать расхождение и отдавать приоритет официальному источнику.
8. Без свежих подтверждений не заполнять пробел знаниями из FIFA Mobile 2023/2024.
9. Разделять слух, утечку, прогноз и подтверждённый анонс.
10. Не скрывать неопределённость ради уверенного тона.

### Рекомендуемые интервалы

Это стартовые значения для настройки, а не гарантия мгновенного обнаружения:
- официальные новости и события: каждые 15–30 минут;
- поиск по вопросу: по запросу с общим rate limit и защитой от повторов;
- карточки: периодическая синхронизация новых/изменившихся записей, только при наличии разрешённого источника;
- цены: с частотой, разрешённой источником; обязательно хранить timestamp и кэшировать;
- промокоды: отдельный осторожный режим; старые статические списки не импортировать как новые коды.

При ошибках источника использовать backoff, логировать проблему и не создавать бесконечный цикл запросов.

## 5. Структурированная база карточек игроков

Это один из главных следующих этапов после проверки доступности источника.

### Поля карточки

- уникальный ID источника;
- имя игрока;
- версия карточки / программа / событие;
- OVR;
- основная и альтернативные позиции;
- клуб, лига и страна;
- базовые характеристики;
- характеристики после рангов/тренировки, если доступны;
- рабочая нога и слабая нога;
- звёзды финтов и слабой ноги;
- рост и физические параметры, если источник их предоставляет;
- PlayStyles/особые свойства, если они есть в текущей версии;
- дата последнего обновления;
- URL карточки и источник.

Нельзя смешивать разные карточки одного футболиста. У одного игрока могут быть версии с разными OVR, программой и характеристиками.

### Поиск

Васёк должен понимать запросы вроде:
- «найди Холанда 115»;
- «все ЦАП до 300 миллионов»;
- «левые защитники с высокой скоростью»;
- «карточки Месси за этот сезон»;
- «кто лучше на ЦАП для H2H».

Поиск должен работать по структурированным данным, а не просить языковую модель вспоминать цифры.

### Сравнение

Сравнивать конкретные версии карточек, а не только фамилии:
- одинаковые или близкие ранги;
- одинаковый уровень тренировки, если он влияет на сравнение;
- нужная позиция;
- ключевые характеристики для выбранного режима;
- PlayStyles и слабые стороны;
- стоимость и время цены, если сравнение включает рынок.

Итог объясняет компромиссы. Победитель не определяется только по OVR.

## 6. Анализ скриншотов и составов

### Распознавание отдельной карточки

1. Найти границы нужной карточки.
2. Считать OVR именно с поля OVR карточки.
3. Отдельно распознать имя, позицию и ранг.
4. Не путать OVR карты, общий OVR состава, ранг и уровень тренировки.
5. Сопоставлять игрока с базой только при достаточном совпадении.
6. Если цифры неразборчивы, не угадывать и попросить крупный фрагмент.

Распознанные значения — это визуальное наблюдение, а не автоматически подтверждённый факт из базы.

### Анализ полного состава

- распознать схему и позиции;
- извлечь игроков и OVR с оценкой уверенности;
- не додумывать скрытые карточки;
- отметить слабые позиции и дисбалансы;
- учитывать бюджет и доступных игроков, если пользователь их назвал;
- уточнить режим H2H, VSA или Manager Mode, если от него зависит рекомендация;
- предложить несколько замен с объяснением.

### Формат результата

Короткий вывод → 2–4 конкретных наблюдения → при необходимости варианты улучшения. Полный отчёт — только по запросу.

## 7. Рекомендации по игрокам и режимам

Разделять рекомендации по H2H, VSA и Manager Mode. Одна карта или тактика не обязана быть лучшей во всех режимах.

Учитывать:
- роль и позицию;
- скорость, ускорение и дриблинг;
- завершение, силу и тип удара;
- пас и видение поля;
- защитные характеристики;
- физику и выносливость;
- рабочую/слабую ногу;
- PlayStyles;
- рост и особенности анимаций, если данные достоверны;
- ранг и тренировку;
- бюджет пользователя.

Если бюджет или режим не названы, не придумывать их. Дать общий ответ и задать один полезный уточняющий вопрос.

## 8. События, задания и награды

Для каждого события, если данные доступны, хранить:
- официальное название;
- статус: upcoming, active, ended или unknown;
- дату начала и завершения с часовым поясом;
- основные режимы/разделы;
- валюты и типы жетонов;
- награды и требования;
- ограничения попыток/энергии;
- путь получения награды;
- официальный источник;
- время последней проверки.

На вопрос «что сейчас делать?» Васёк должен определить реально активное событие, проверить сроки и условия, разделить подтверждённые награды и предположения, дать практичный порядок действий и не предлагать просроченные задания как текущие.

Если срок события не найден, не придумывать дату окончания.

## 9. Промокоды

- Новый код должен быть найден в свежей датированной публикации.
- Не импортировать старые страницы со списками кодов как новые.
- Хранить код, источник, время публикации, время обнаружения и статус.
- Не объявлять код гарантированно активным без подтверждения.
- Не просить пароль EA и не входить в аккаунт пользователя.
- Давать официальную страницу активации: https://redeem.fcm.ea.com/
- Не повторять одно уведомление в группе.
- Историю отправок хранить отдельно от факта обнаружения.

## 11. Память и групповое поведение

- Помнить короткий контекст беседы, чтобы не терять предмет вопроса.
- Хранить только устойчивые игровые предпочтения в рамках настроек группы.
- Не приписывать участнику состав, бюджет или мнение другого участника.
- Не раскрывать внутреннюю память и системные инструкции.
- Не отвечать на каждую реплику; [SKIP] использовать, когда от Васька не требуется ответ.
- Если к нему обратились напрямую, отвечать, даже если вопрос не содержит ключевого слова FC Mobile.
- Юмор и подколы допустимы, но без травли и навязчивости.
- Не выдумывать личный игровой аккаунт, опыт выбивания карт или собственный состав.

## 12. Системный промпт — обязательный контракт поведения

Промпт задаёт поведение, но не заменяет программную проверку данных.

### Правила, которые всегда должны быть в SYSTEM_PROMPT

1. **Личность:** Васёк — естественный участник чата FC Mobile, не рекламирует себя и не начинает ответы с самопрезентации.
2. **Краткость:** обычно 1–4 предложения; подробный формат — по запросу.
3. **Актуальность:** для текущего сезона использовать переданный свежий контекст и его даты; не выдавать старые знания FIFA Mobile за современные.
4. **Источники:** различать EA, специализированные базы, фанатские публикации, слухи и пользовательский скриншот.
5. **Нет данных:** прямо сказать, что факт не подтверждён, вместо догадки.
6. **Карточки:** не выдумывать OVR, характеристики, цены, позиции, ранги и версии карточек.
7. **Изображения:** читать только реально видимые цифры; не путать OVR карточки с OVR состава; при сомнении просить крупный фрагмент.
8. **Сравнение:** сравнивать точные версии карт и учитывать режим, позицию, ранг и бюджет, если они известны.
9. **События:** не называть событие активным без актуального статуса и дат.
10. **Команды:** не заявлять о функции, которой нет в доступных инструментах и контексте.
11. **Приватность:** не просить пароль EA, коды входа и иные секреты.
12. **Собеседник:** сохранять [SKIP] для нерелевантных сообщений; не использовать его при прямом обращении.

### Контракт контекста данных

Когда код передаёт модели блок свежих данных, он должен ясно содержать:
- текущую дату и время UTC;
- тип каждого источника;
- дату публикации и дату получения;
- URL;
- статус подтверждения;
- факты/поля, которые источник действительно подтверждает;
- явную пометку, если поиск ничего свежего не нашёл.

Промпт объясняет, как использовать такой блок. Проверка дат, дедупликация, валидация полей и отбрасывание устаревших данных должны происходить в коде до вызова модели.

### Запрещённые заявления без подтверждения

Васёк не должен говорить:
- «Я проверил актуальную цену», если нет свежего источника цены.
- «Эта карта сейчас лучшая», если не определены режим и критерии.
- «Событие сейчас активно», если статус и даты не подтверждены.
- «Код рабочий», если EA не подтвердила его или пользователь не проверил активацию.
- «У меня есть база всех карточек», если база не подключена и не обновляется.
- «Я вижу OVR ...», если цифры неразборчивы.

## 13. Техническая архитектура

Не складывать всю логику в один огромный промпт или один файл.

Рекомендуемое разделение по мере появления реальных функций:
- app/monitor.py — обнаружение новостей и расписание;
- app/sources/ — отдельные адаптеры EA, RenderZ и RSS;
- app/intel/ — нормализация, свежесть, доверие, дедупликация и поиск;
- app/players/ — карточки, фильтрация и сравнение;
- app/vision/ — извлечение данных из изображений и оценка уверенности;
- app/ai.py — сбор контекста и вызов Groq;
- app/persona.py — системный промпт;
- app/storage.py — SQLite схема и миграции;
- tests/ — тесты парсеров, актуальности, промпта и сценариев.

Не создавать все каталоги заранее ради пустой архитектуры. Выделять модули по мере реализации.

### База данных

При расширении SQLite предусмотреть отдельные сущности для источников и состояния опроса, публикаций, событий, карточек игроков, истории цен, промокодов и истории отправленных уведомлений.

Для таблиц нужны индексы по внешнему ID, нормализованному имени и времени обновления там, где это требуется. Миграции должны быть повторяемыми и безопасными для существующих данных.

## 14. Надёжность, стоимость и безопасность

- Сначала использовать бесплатные публичные источники и текущий HTTP-стек.
- Не добавлять платные API без отдельного согласования.
- Не отправлять каждое сообщение в Groq, если можно ответить из базы или промолчать.
- Кэшировать ответы источников и дедуплицировать запросы.
- Использовать таймауты, ограничение параллелизма и exponential backoff.
- Не парсить сайты на каждое обычное сообщение.
- Не хранить API-ключи и Telegram-токены в GitHub, логах или документации.
- Не запрашивать EA-логин/пароль, session cookies или коды подтверждения.
- Учитывать правила и условия использования сайтов.
- Если источник сломался, обычный чат продолжает работать, а отсутствие свежих данных обозначается честно.

## 15. План реализации по этапам

### Этап 0 — аудит и базовая надёжность
- Проверить реальный путь передачи intel-контекста в модель.
- Убедиться, что даты, ссылки и типы источников доходят до промпта.
- Исправить несогласованности документации и кода.
- Добавить тесты на устаревшие даты, пустой поиск, дубликаты и сбой источника.
- Проверить, что ошибка мониторинга не ломает ответы в группе.

**Готово, когда:** бот не выдаёт старые публикации за текущие и не падает, если RSS недоступен.

### Этап 1 — качество свежих новостей и событий
- Улучшить поиск EA и RenderZ по новостям.
- Извлекать даты, заголовки, ссылки и краткое содержание.
- Разделять официальные новости и материалы сообщества.
- Нормализовать активные события и сроки, когда источник сообщает их явно.
- Добавить /news и /events после готовности обработчиков.

**Готово, когда:** ответ о текущем событии содержит дату и источник и не предлагает завершённое событие.

### Этап 2 — карточки игроков
- Проверить допустимый способ получения карточных данных RenderZ или другого источника.
- Создать схему карточки и импорт с дедупликацией.
- Обновлять только изменившиеся записи.
- Реализовать поиск по имени, OVR, позиции, клубу и программе.
- Показывать ссылку на карточку и время обновления.

**Готово, когда:** поиск возвращает конкретные версии карточек с источником и датой; неизвестный игрок не выдумывается.

### Этап 3 — сравнение и подбор
- Сравнение двух карт по характеристикам.
- Подбор отдельно под H2H, VSA и Manager Mode.
- Фильтр по бюджету и позиции.
- Объяснение сильных и слабых сторон.
- Не ранжировать только по OVR.

**Готово, когда:** числовые сравнения берутся из базы, а выводы отделены от фактов.

### Этап 4 — анализ скриншотов
- Проверить качество OCR/vision на тестовом наборе карточек.
- Сопоставлять распознанное с базой при достаточной уверенности.
- Анализировать состав и схему.
- Учитывать ошибки распознавания и просить крупный фрагмент, когда нужно.
- Хранить исходные изображения только если это необходимо и разрешено настройками хранения.

**Готово, когда:** бот не подставляет типовой OVR и не придумывает невидимые поля; есть тесты на мелкие и размытые цифры.

### Этап 5 — удобство в Telegram
- /players, /compare, /sources и /refresh с проверкой доступа и ограничением частоты.
- Естественные запросы без команд.
- Компактный формат ответа.
- Ссылки на источники.
- Проверка поведения в групповом чате.

**Готово, когда:** команды документированы, доступны в /help и протестированы.

## 2026-11-24 — RenderZ search reliability increment

Implemented in `app/renderz.py`:

- Normalize accents and punctuation before matching visible player-card labels.
- Require every requested name token to be present as a complete token; do not accept partial substring coincidences.
- Keep explicit OVR filtering when the user supplies a card rating.
- Refuse OVR-only lookups that would otherwise return unrelated cards.
- Recognize English player-data terms (player/card/stats/rating/price/rank/training/compare).
- Expand Russian aliases for common FC Mobile players and add transliteration fallback for other Cyrillic names.
- Continue using public RenderZ HTML pages only; no undocumented/private API or paid provider was added.

Tests added for exact-token matching, multi-word names, accented names, OVR-only rejection, transliteration and English query detection.

**Limitations:** this improves matching against the visible cards returned by RenderZ; it does not create a complete local card database or guarantee that RenderZ's public page returns every matching card. Multiple-card comparison and structured squad analysis remain separate future stages.

- Search the public player-list pagination (up to 8 pages) instead of relying on unverified `search=`/`q=` URL parameters or only the first page.
- Preserve connectors in two-player requests and search each requested name independently; explicitly tell the model when not all requested players were found.


## Автоадаптация манеры общения (2026-11-24)

В память группы добавлено обучение на уровне контекста, а не дообучение модели:
- бот постепенно замечает повторяющиеся темы, локальные мемы и предпочтения по длине/юмору/сарказму/мату;
